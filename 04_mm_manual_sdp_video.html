Demo 3 — Manual SDP Video Call

04_mm_manual_sdp_video.html · No server required · Google STUN · P2P video

This demo makes a real P2P video call between two browser tabs using manual SDP copy-paste as the signaling channel. You will perform the signaling yourself — copying the offer SDP from the Caller tab into the Callee tab, then copying the answer back. This makes the normally-invisible signaling process completely transparent.

What you are doing manually here is exactly what a signaling server automates in Demo 5. The data is the same — an SDP offer, an SDP answer, and a stream of ICE candidates. The only difference is the transport: here you copy-paste; in Demo 5, WebSocket sends it automatically.
// CONCEPT: Manual signaling
A signaling server is just a message relay. It takes the offer from Peer A and delivers it to Peer B, then takes the answer and delivers it back. Nothing about the SDP or ICE data changes — only the transport. This demo uses you as the signaling transport.
Requires camera + microphone. The browser will ask for permission when you click Start Call. Both tabs must grant access. For a real cross-network call, open each tab on a different machine. On the same machine, you will call yourself — you will see your own video in the remote pane (and your microphone and speaker may create echo; use headphones).

How to use this demo

  1. Open this file in two browser tabs.
  2. In Tab 1, click "I am the Caller (Tab A)" and follow the Caller steps.
  3. In Tab 2, click "I am the Callee (Tab B)" and follow the Callee steps.
  4. Copy-paste SDP and ICE candidates between tabs as each step instructs.
  5. Watch the video appear and the connection state turn green.

For a cross-network call: open Tab A on one machine, Tab B on another machine, and share the textareas contents via any text channel (chat, email, notes).

// CONCEPT: Trickle ICE
ICE candidates do not all arrive before the offer/answer exchange. They trickle in asynchronously after setLocalDescription() triggers ICE gathering. You will see the candidate list grow over a few seconds. Each new candidate must be sent to the remote peer and added via addIceCandidate(). The null candidate (end-of-gathering signal) fires when all candidates have been gathered — but with trickle ICE you do not need to wait for it.
// CONCEPT: srflx candidate — STUN at work
Look at the ICE candidates that appear. You will see candidates of type host (your local LAN IP) and, if you are behind NAT, candidates of type srflx (server-reflexive — your public IP as seen by the Google STUN server). The STUN server did exactly one thing: it told you what your public IP:port looks like from the outside. On the same LAN you will only see host candidates. relay candidates would require a TURN server (see Demo 6).
