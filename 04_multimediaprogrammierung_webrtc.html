Chapter 04: WebRTC

WebRTC (Web Real-Time Communication) is a collection of open standards built into every modern browser that enables peer-to-peer audio, video, and data transfer — entirely in JavaScript, with no plugins and no native apps. Two browser tabs on opposite sides of the world can open a direct connection, exchange a live video stream, and send arbitrary binary data, all without any media traffic passing through a server.

What makes WebRTC remarkable is what it hides: NAT traversal, DTLS encryption, RTP packetisation, codec negotiation, congestion control, and adaptive bitrate are all handled automatically by the browser. What you write is a few dozen lines of JavaScript. What the browser does underneath is decades of real-time networking research.

This chapter teaches WebRTC from the ground up — the networking problems it solves, the protocols it uses, and the browser API that exposes them — through seven escalating hands-on demos.

1. What is WebRTC and Why Does It Exist

Before WebRTC, real-time communication in the browser required Flash, Java applets, or proprietary browser plugins. These were slow to install, insecure, and unavailable on mobile. In 2010, Google acquired two companies — GIPS (audio/video processing) and On2 Technologies (video codecs) — and open-sourced the combined technology stack. The W3C and IETF standardised the browser API and the underlying protocols. By 2012, Chrome and Firefox shipped the first implementations. Today, WebRTC is built into every major browser with no installation required.

Where WebRTC is used in industry

ApplicationHow WebRTC is used
Video conferencingGoogle Meet, Discord, Whereby — all built on WebRTC peer connections
Live streamingSub-second latency streams (WHIP/WHEP protocol uses WebRTC as transport)
Remote desktopScreen sharing and remote control over DataChannel
Broadcast contributionCamera-to-server ingest at broadcasters using WebRTC instead of satellite
IoT and telemetryLow-latency data from sensors via DataChannel
Multiplayer gamingPeer-to-peer game state synchronisation

The three pillars of WebRTC

WebRTC is built on three independent capabilities that work together:

  1. Media capture — getUserMedia() and getDisplayMedia() give you access to the camera, microphone, and screen as MediaStream objects.
  2. Peer connection — RTCPeerConnection establishes an encrypted, direct connection between two browsers, handles NAT traversal via ICE, negotiates codecs via SDP, and transports media via RTP.
  3. Data channels — RTCDataChannel adds a bidirectional, low-latency data transport (SCTP over DTLS) alongside the media streams. You can send text, JSON, binary blobs — anything.

What WebRTC deliberately does not provide

WebRTC has no built-in mechanism for two peers to find each other. Before a peer connection can be established, the two browsers must exchange some setup information (called an offer and answer) through some out-of-band channel. This channel is called the signaling channel, and WebRTC leaves its implementation entirely to the application. You can use WebSocket, HTTP, email, SMS, or even copy-paste — WebRTC does not care. This is a deliberate design choice: it gives applications full freedom over authentication, room management, and transport.

Connection to earlier chapters. The Web Audio API (Chapter 01) models audio as a graph of processing nodes. WebRTC extends this idea to the network: a MediaStreamTrack from getUserMedia() can be fed directly into an RTCPeerConnection, which transports it to a remote peer whose browser can feed it into a Web Audio processing graph. The two APIs are designed to compose.

2. NAT and the Peer Connectivity Problem

The fundamental networking challenge WebRTC must solve is that most devices on the internet do not have a publicly reachable IP address. They sit behind a Network Address Translator (NAT) — typically a home router or corporate firewall — that shares a single public IP address among many private devices.

How NAT works

When your laptop (private IP 192.168.1.5) opens a connection to a web server, your router translates the source address to its public IP (say 87.100.42.7) and records the mapping in a translation table:

Private address          Public address        Destination
192.168.1.5:54321   →   87.100.42.7:54321  →  93.184.216.34:443

When the server replies to 87.100.42.7:54321, the router looks up the table and forwards the packet to 192.168.1.5:54321. This works perfectly for client-initiated connections — which is all HTTP, WebSocket, and most internet traffic.

The problem arises with peer-to-peer connections. If Peer A (behind NAT A) wants to send a packet directly to Peer B (behind NAT B), it does not know B's public IP:port — B's router has not created a mapping for that destination yet. And even if A somehow knew B's public address, B's router would drop the incoming packet because it has no table entry for it.

NAT types and traversal difficulty

NAT typeInbound ruleTraversal
Full coneAccepts packets from any source once an outbound mapping existsEasy — STUN is sufficient
Address-restricted coneAccepts packets only from addresses the client previously sent toSTUN with hole-punching
Port-restricted coneAccepts packets only from the exact address:port previously sent toSTUN with hole-punching
Symmetric NATCreates a different public port for each destination — no hole-punch possibleRequires TURN relay

Corporate networks frequently use symmetric NAT and block all UDP traffic at the firewall. This is why WebRTC needs both STUN (for most cases) and TURN (for the hard cases).

ICE, STUN, and TURN exist because of NAT. Without NAT, every device would have a public IP and peers could connect directly. The entire ICE/STUN/TURN stack is a workaround for the IP address exhaustion problem that led to NAT being deployed everywhere. IPv6 removes the need for NAT entirely — but IPv6 adoption is still incomplete, so WebRTC must handle IPv4 NAT for the foreseeable future.

3. ICE — Interactive Connectivity Establishment

ICE (RFC 8445) is the framework WebRTC uses to find a working network path between two peers. Rather than guessing, ICE takes a systematic approach: it gathers every possible address a peer might be reachable at, exchanges that list with the remote peer, and then tries every combination until one works.

ICE candidate types

Each address ICE considers is called a candidate. There are three types:

TypeAddress sourceWhen it worksPriority
hostThe peer's local network interface (e.g. 192.168.1.5:54321)Both peers on the same LANHighest
srflx (server reflexive)The peer's public IP:port as seen by a STUN serverPeers on different networks with NAT that permits hole-punchingMedium
relayAn address on a TURN server that relays all trafficAlways — but all media goes through the relay serverLowest

The ICE gathering process

When setLocalDescription() is called on an RTCPeerConnection, the browser begins ICE gathering:

  1. It collects host candidates from every local network interface (WiFi, Ethernet, loopback).
  2. It contacts the configured STUN server and records the public IP:port it receives back — this becomes the srflx candidate.
  3. If a TURN server is configured, it authenticates and requests an allocation — the allocated relay address becomes the relay candidate.
  4. Each candidate is reported to the application via the onicecandidate event as it is discovered. When gathering is complete, onicecandidate fires with event.candidate === null.

Trickle ICE vs. vanilla ICE

In vanilla ICE, the peer waits until all candidates are gathered before sending the SDP to the remote peer. In trickle ICE (the modern standard), candidates are sent to the remote peer as they are discovered — via the signaling channel — without waiting for gathering to complete. Trickle ICE significantly reduces call setup time because connectivity checks can begin before the slowest candidate (TURN allocation) has arrived.

The onicecandidate event is the hook for trickle ICE: each time it fires with a non-null candidate, send that candidate to the remote peer via the signaling channel, and call addIceCandidate() on the remote peer's connection.

ICE connectivity checks

Once both peers have each other's candidate lists, ICE performs connectivity checks: it sends STUN binding requests from every local candidate to every remote candidate and waits for a response. The highest-priority candidate pair that succeeds in both directions is nominated as the active path. All media then flows through the nominated pair.

// The onicecandidate event fires once per candidate as ICE gathers them.
// Each candidate is an RTCIceCandidate object with a .candidate string
// that encodes the type, address, port, priority, and protocol.

peerConnection.onicecandidate = (event) => {
  if (event.candidate === null) {
    // Gathering is complete — all candidates have been reported.
    console.log('ICE gathering complete');
    return;
  }

  // event.candidate.type is 'host', 'srflx', or 'relay'
  // event.candidate.address is the IP address (may be mDNS on Chrome for privacy)
  // event.candidate.port is the port number
  // event.candidate.protocol is 'udp' or 'tcp'
  console.log(`New ICE candidate: type=${event.candidate.type}`);

  // In trickle ICE, send this candidate to the remote peer immediately
  // via the signaling channel, rather than waiting for all candidates.
  signalingChannel.send(JSON.stringify({
    type: 'ice',
    candidate: event.candidate.toJSON()
  }));
};
ICE candidate priority. The priority of a candidate is a 32-bit number calculated as: (type_preference × 2²⁴) + (local_preference × 2⁸) + component. The browser assigns type_preference values of 126 for host, 100 for srflx, and 0 for relay. This ensures that direct paths are always preferred over relay paths, and local paths are preferred over public ones.

4. STUN — Session Traversal Utilities for NAT

STUN (RFC 8489) is a lightweight request-response protocol with one job: tell a client what its public IP address and port look like from outside its NAT. A STUN server is a simple UDP/TCP server on a public IP that reads the source address of incoming packets and echoes it back in the response.

How a STUN binding request works

  1. The browser opens a UDP socket on a local port (e.g. 192.168.1.5:54321).
  2. It sends a Binding Request to the STUN server at stun.l.google.com:19302.
  3. The STUN server receives the packet. The source address in the IP header is the NAT's public translation: 87.100.42.7:54321.
  4. The STUN server sends a Binding Response containing 87.100.42.7:54321.
  5. The browser now knows its public address and includes it as an srflx candidate in the SDP.

That is the entire STUN protocol for the common case. It is stateless: the server forgets about the exchange as soon as it sends the response.

What STUN does not do

STUN only discovers the public address. It does not relay traffic. Once both peers know each other's public address (from the SDP exchange), they attempt to send packets directly to each other — this is called NAT hole-punching. For full-cone, address-restricted, and port-restricted NAT, this works. For symmetric NAT, it does not — because each outbound connection gets a different public port, so the address in the SDP is only valid for the specific destination it was created for (the STUN server), not for the peer.

// The RTCConfiguration tells the browser which STUN and TURN servers to use.
// The browser's ICE agent contacts these servers automatically during gathering.

const configuration = {
  iceServers: [
    {
      // Google's public STUN server — free, reliable, no credentials required.
      // Used in development and in many production deployments.
      urls: 'stun:stun.l.google.com:19302'
    }
    // TURN server would go here as a second entry (see Section 5)
  ]
};

const peerConnection = new RTCPeerConnection(configuration);
STUN is cheap; TURN is expensive. A STUN transaction is a single round-trip of two small UDP packets. The STUN server uses minimal bandwidth and CPU. A TURN relay, by contrast, carries all media traffic — every video frame and audio packet passes through it. This is why ICE always prefers host and srflx candidates over relay candidates. TURN is the last resort.

5. TURN — Traversal Using Relays around NAT

When ICE cannot find a direct path between peers — because both are behind symmetric NAT, or because a firewall blocks all inbound UDP — it falls back to a TURN relay. The TURN server (RFC 8656) sits on a public IP, allocates a relay address for each peer, and forwards all traffic between them. From the perspective of each peer's NAT, the traffic looks like an outbound connection to the TURN server — which is always permitted.

How TURN works

  1. Authentication — the browser sends a TURN Allocate request with credentials (username + password). The server verifies the credentials and allocates a relay address (a public IP:port on the TURN server).
  2. Relay address as ICE candidate — the relay address becomes a relay candidate in the SDP. Both peers exchange their relay addresses via signaling.
  3. Media relay — once connectivity checks confirm the relay path works, all media flows from Peer A → TURN server → Peer B and back. Neither peer sends traffic directly to the other.

TURN credentials

TURN always requires authentication to prevent abuse (an open TURN server would be exploited as a free bandwidth relay). Two credential models exist:

ModelHow it worksUse case
Long-term credentialsStatic username and password configured on the server. Simple, but credentials cannot be revoked per-session.Development, course environments (this chapter)
Time-limited credentialsUsername encodes a timestamp; password is HMAC-SHA1(secret, username). Credentials expire automatically.Production — backend generates fresh credentials per session

TURN transport modes

ModeTransportPortWhen to use
TURN/UDPUDP3478Default — lowest latency, best performance
TURN/TCPTCP3478When UDP is blocked by a firewall
TURNS/TCPTLS over TCP5349When only HTTPS traffic is permitted (corporate firewalls, Codespaces)

In this course we use TURNS over TCP/TLS because GitHub Codespaces port forwarding is HTTP-based and cannot forward raw UDP. TURNS is a legitimate production configuration — many enterprise deployments use it for exactly the same reason: strict firewalls that permit only TLS traffic.

// The browser tries all iceServers entries in parallel during ICE gathering.

  iceServers: [
    {
      // STUN — no credentials needed, used to discover srflx candidates

    },

      // 'turns:' prefix means TURNS (TURN over TLS/TCP) — suitable for Codespaces

      // Long-term credentials (as configured in coturn.conf)
      username: 'webrtc',
      credential: 'seminar04'
    }
  ]
};

// iceTransportPolicy controls which candidate types ICE will use.
// 'all' (default): use host, srflx, and relay candidates — prefers direct paths.
// 'relay': use ONLY relay candidates — forces all traffic through TURN.
//          Useful for testing TURN, for privacy (hides real IP), or for
//          corporate networks that block all UDP.
const configuration_force_relay = {
  iceServers: [ /* ... */ ],
  iceTransportPolicy: 'relay'  // Force TURN — no direct paths allowed
};

6. SDP — Session Description Protocol

SDP (RFC 8866) is the text format that peers use to describe what they want to send and receive: which codecs they support, which network addresses they are reachable at, which security parameters to use. It is not a negotiation protocol — it is a description format. The negotiation (the offer/answer exchange) is defined separately in the JavaScript Session Establishment Protocol (JSEP, RFC 8829).

Anatomy of a WebRTC SDP offer

An SDP document is a sequence of lines, each in the form type=value. Here is a minimal annotated example:

v=0                          ; SDP version — always 0
o=- 12345 2 IN IP4 127.0.0.1 ; origin: session-id, version, network type, address
s=-                          ; session name — unused in WebRTC, set to '-'
t=0 0                        ; timing: start and stop time (0 = unbounded)

; === Audio media section ===
m=audio 9 UDP/TLS/RTP/SAVPF 111 103
; m= type port proto fmt-list
; port 9 is a dummy (actual address comes from ICE candidates)
; UDP/TLS/RTP/SAVPF = DTLS-encrypted RTP with feedback

a=rtpmap:111 opus/48000/2    ; payload type 111 = Opus codec, 48kHz, stereo
a=fmtp:111 minptime=10;useinbandfec=1  ; Opus parameters: min frame 10ms, FEC on

a=ice-ufrag:xK3y             ; ICE username fragment — part of the ICE credentials
a=ice-pwd:vNd2kLm9zXqR...    ; ICE password — shared secret for this session
a=fingerprint:sha-256 AA:BB: ; DTLS certificate fingerprint — used for verification
a=setup:actpass              ; this peer can be either DTLS client or server
a=mid:audio                  ; media stream identifier

; ICE candidates (in trickle ICE, these arrive separately via signaling)
a=candidate:1 1 udp 2130706431 192.168.1.5 54321 typ host
;             ^ ^ ^   priority   address     port  type
a=candidate:2 1 udp 1694498815 87.100.42.7 54321 typ srflx raddr 192.168.1.5 rport 54321
;             srflx = server-reflexive = our public IP as seen by STUN

; === Video media section ===
m=video 9 UDP/TLS/RTP/SAVPF 96 97
a=rtpmap:96 VP8/90000         ; payload type 96 = VP8 video codec
a=rtpmap:97 H264/90000        ; payload type 97 = H.264 video codec
a=rtcp-fb:96 nack             ; negative acknowledgement (retransmission)
a=rtcp-fb:96 nack pli         ; picture loss indication (keyframe request)

The offer/answer model

Establishing a WebRTC connection requires an offer from one peer and an answer from the other. The sequence is:

  1. Caller calls createOffer() — browser generates an SDP offer describing its capabilities.
  2. Caller calls setLocalDescription(offer) — ICE gathering begins; the offer is stored locally.
  3. Caller sends the offer to the callee via the signaling channel.
  4. Callee calls setRemoteDescription(offer) — callee learns what the caller wants.
  5. Callee calls createAnswer() — browser generates an answer from the intersection of both sets of capabilities.
  6. Callee calls setLocalDescription(answer) — callee's ICE gathering begins.
  7. Callee sends the answer to the caller via the signaling channel.
  8. Caller calls setRemoteDescription(answer) — the negotiation is complete; connectivity checks begin.
// ── Caller side ──────────────────────────────────────────────

// createOffer() returns a Promise resolving to an RTCSessionDescription.
// The SDP is generated by the browser based on the tracks added to the connection
// and the RTCConfiguration (STUN/TURN servers).
const offer = await peerConnection.createOffer();

// setLocalDescription() stores the offer and begins ICE gathering.
// After this call, onicecandidate will start firing.
await peerConnection.setLocalDescription(offer);

// Send the offer SDP to the remote peer via your signaling channel.
// In demos 1–3 this is copy-paste; in demos 5–7 it is a WebSocket message.
signalingChannel.send(JSON.stringify({ type: 'offer', sdp: offer.sdp }));


// ── Callee side (after receiving the offer) ───────────────────

// setRemoteDescription() stores the remote peer's offer.
// Must be called before createAnswer().
await peerConnection.setRemoteDescription(new RTCSessionDescription(offer));

// createAnswer() generates an SDP answer from the intersection of capabilities.
const answer = await peerConnection.createAnswer();

// Store the answer locally and begin ICE gathering on the callee side.
await peerConnection.setLocalDescription(answer);

// Send the answer back to the caller.
signalingChannel.send(JSON.stringify({ type: 'answer', sdp: answer.sdp }));
SDP is verbose, but read it at least once. Most developers never look at raw SDP — the browser generates and parses it automatically. But reading it helps you understand codec negotiation failures, why certain browsers fall back to different codecs, and what DTLS fingerprints are for. Demo 1 displays the raw SDP offer and answer so you can inspect them.

7. RTCPeerConnection — The Core API

RTCPeerConnection is the central object in the WebRTC browser API. It encapsulates the entire connection lifecycle: ICE negotiation, DTLS handshake, codec selection, RTP media transport, RTCP feedback, and DataChannel SCTP transport. You interact with it through a set of methods and event handlers.

Key events

EventWhen it firesWhat to do
onicecandidateEach time ICE discovers a new candidate (or finishes gathering)Send the candidate to the remote peer via signaling
oniceconnectionstatechangeICE connection state changesMonitor for failed — consider ICE restart
onconnectionstatechangeOverall connection state changesUpdate UI; handle failed with reconnection logic
onnegotiationneededA track was added/removed and renegotiation is neededCreate and send a new offer
ontrackA remote media track arrivesAttach event.streams[0] to a <video> element
ondatachannelThe remote peer created a DataChannelStore the channel; set up its event handlers

The connection state machine

The connectionState property follows this lifecycle. Understanding each state is essential for building reliable applications:

StateMeaning
newConnection created; no ICE gathering has started yet
connectingICE and DTLS are in progress
connectedAt least one ICE candidate pair is working and DTLS is complete — media is flowing
disconnectedThe network temporarily lost packets. ICE is trying to recover. May return to connected.
failedICE could not find a working path, or the path permanently failed. Action required: ICE restart.
closedclose() was called. Resources released. Cannot be reused.
 
// Monitor the connection state — this is the most important event handler
// for building reliable WebRTC applications.
peerConnection.onconnectionstatechange = () => {
  const state = peerConnection.connectionState;
  console.log('Connection state:', state);

  switch (state) {
    case 'connected':
      // Media is flowing. Update the UI to show the call is active.
      showCallActive();
      break;

    case 'disconnected':
      // Temporary network interruption. ICE may recover automatically.
      // Show a "reconnecting..." indicator but do not tear down the call yet.
      showReconnecting();
      break;

    case 'failed':
      // ICE gave up. The connection cannot recover on its own.
      // Trigger an ICE restart: generates new ICE credentials and
      // re-runs connectivity checks without tearing down the media session.
      peerConnection.restartIce();
      // restartIce() triggers onnegotiationneeded → create and send a new offer.
      break;

    case 'closed':
      // The connection was explicitly closed. Clean up the UI.
      showCallEnded();
      break;
  }
};

// addTrack() adds a local media track to the connection.

8. getUserMedia — Capturing Camera, Microphone, and Screen

navigator.mediaDevices.getUserMedia() requests access to the user's camera and microphone. It returns a Promise that resolves to a MediaStream — a collection of MediaStreamTrack objects, one per input device. The browser shows a permission dialog; if the user denies, the Promise rejects.

Constraints — requesting what you need

The constraints object tells the browser what you want. The browser provides the closest match it can. You can specify ideal values, minimum values, or exact requirements:

// Basic constraints — request both video and audio
const stream = await navigator.mediaDevices.getUserMedia({
  video: true,  // any camera
  audio: true   // any microphone
});

// Detailed constraints — specify resolution, frame rate, and audio processing
const stream = await navigator.mediaDevices.getUserMedia({
  video: {
    width:  { ideal: 1280 },    // prefer 720p width, accept anything
    height: { ideal: 720 },
    frameRate: { ideal: 30, max: 60 },

    // Request a specific camera by its deviceId (from enumerateDevices)
    deviceId: { exact: selectedDeviceId }
  },
  audio: {
    echoCancellation: true,   // remove echo from the speaker playing in the room
    noiseSuppression: true,   // filter background noise
    autoGainControl:  true,   // normalise microphone volume
    sampleRate: { ideal: 48000 }
  }
});

9. RTCDataChannel — Peer-to-Peer Data

RTCDataChannel provides a bidirectional peer-to-peer data transport built on SCTP over DTLS. Once a peer connection is established, you can send arbitrary text or binary data — JSON messages, file chunks, game state, subtitles — with very low latency and no server involvement. The data channel shares the same DTLS session as the media tracks, so no additional connection setup is needed.

Delivery modes

OptionBehaviourAnalogous to
ordered: true (default)Messages arrive in order; lost messages are retransmittedTCP
ordered: falseMessages may arrive out of order; no retransmissionUDP
maxRetransmits: NRetransmit at most N times, then discardUDP with limited retry
maxPacketLifeTime: msDiscard messages older than this many millisecondsReal-time data with expiry
 
// ── Offerer side: create the channel BEFORE calling createOffer() ──
// Creating the channel before the offer ensures it appears in the SDP
// (as an m=application section) so the answerer knows to expect it.

const dataChannel = peerConnection.createDataChannel('chat', {
  ordered: true       // guarantee delivery order (TCP-like)
  // maxRetransmits: 0  // use this for real-time data that must not be delayed
});

// DataChannel lifecycle events
dataChannel.onopen = () => {
  // Channel is ready — both peers have completed the SCTP handshake.
  // Only send data after onopen fires; sending before open is silently dropped.
  console.log('DataChannel open');
  dataChannel.send('Hello from the offerer!');
};

dataChannel.onmessage = (event) => {
  // event.data is a string, ArrayBuffer, or Blob depending on what was sent.
  console.log('Received:', event.data);
};

dataChannel.onclose = () => console.log('DataChannel closed');
dataChannel.onerror = (error) => console.error('DataChannel error:', error);


// ── Answerer side: receive the channel via ondatachannel ──
// The answerer does NOT call createDataChannel().
// Instead, the browser fires ondatachannel when the channel is negotiated.

peerConnection.ondatachannel = (event) => {
  const remoteChannel = event.channel;
  remoteChannel.onopen    = () => remoteChannel.send('Hello back!');
  remoteChannel.onmessage = (e) => console.log('Received:', e.data);
};

// Sending different data types
dataChannel.send('plain text message');
dataChannel.send(JSON.stringify({ type: 'position', x: 100, y: 200 }));

// Binary data — send an ArrayBuffer
const buffer = new Uint8Array([1, 2, 3, 4]).buffer;
dataChannel.send(buffer);
Connection to earlier chapters. RTCDataChannel is conceptually similar to the browser's MessageChannel API — both provide bidirectional message passing. The key difference is that DataChannel works across the network, peer-to-peer, with no server in the middle once the WebRTC connection is established.

10. Signaling — The Missing Piece

Before two peers can establish a WebRTC connection, they must exchange three things:

  1. The offer SDP from the caller to the callee.
  2. The answer SDP from the callee back to the caller.
  3. ICE candidates from each peer to the other (in both directions, in trickle ICE mode).

This exchange requires some out-of-band channel — a channel that exists before the WebRTC connection. WebRTC calls this the signaling channel and deliberately leaves its implementation to the application.

Our WebSocket signaling server

The signaling server in codespace/signaling_server.py is intentionally minimal: it routes JSON messages between two peers in the same room. It has no knowledge of SDP or ICE — it is a dumb router. The message format is:

// All signaling messages use this JSON structure.
// The server reads 'type' to know whether to broadcast or route,
// and 'room' to know which peer to forward to.
{
  "type":  "join" | "offer" | "answer" | "ice",
  "room":  "room1",     // room identifier — both peers must use the same room
  "data":  { ... }      // the SDP object or ICE candidate object
}

The full server source code with line-by-line comments is in Section 12 below.

ICE candidate timing: a critical subtlety

In trickle ICE, ICE candidates from the remote peer may arrive via the signaling channel before setRemoteDescription() has been called on your peer connection. If you call addIceCandidate() before setRemoteDescription(), the browser throws an error. The solution is to queue incoming candidates and add them after setRemoteDescription() completes:

// Queue for ICE candidates that arrive before setRemoteDescription()
const pendingCandidates = [];
let remoteDescriptionSet = false;

signalingChannel.onmessage = async (event) => {
  const message = JSON.parse(event.data);

  if (message.type === 'ice') {
    if (remoteDescriptionSet) {
      // Safe to add immediately
      await peerConnection.addIceCandidate(new RTCIceCandidate(message.data));
    } else {
      // Queue it — will be added after setRemoteDescription()
      pendingCandidates.push(message.data);
    }
  }

  if (message.type === 'answer') {
    await peerConnection.setRemoteDescription(new RTCSessionDescription(message.data));
    remoteDescriptionSet = true;

    // Drain the queue — add all candidates that arrived early
    for (const candidate of pendingCandidates) {
      await peerConnection.addIceCandidate(new RTCIceCandidate(candidate));
    }
    pendingCandidates.length = 0;
  }
};

11. getStats() — Monitoring a Live Connection

RTCPeerConnection.getStats() returns a detailed snapshot of the connection's internal state. It is the primary tool for diagnosing WebRTC quality issues in production — the programmatic equivalent of Chrome's chrome://webrtc-internals.

How to read the stats report

// getStats() returns a Promise resolving to an RTCStatsReport — a Map
// where each value is a stats object with a 'type' property.
const report = await peerConnection.getStats();

report.forEach((stats) => {
  // Each stats entry has a unique 'id' and a 'type'.
  // Filter by type to find the data you need.
  switch (stats.type) {

    case 'inbound-rtp':
      // Stats for media being received from the remote peer.
      // bytesReceived: cumulative bytes (not rate — see bitrate calculation below)
      // packetsLost: cumulative lost packets (use for packet loss percentage)
      // jitter: variance in inter-packet arrival time (in seconds)
      // framesDecoded: for video — total frames decoded
      console.log(`Inbound: ${stats.bytesReceived} bytes, ${stats.packetsLost} lost`);
      break;

    case 'outbound-rtp':
      // Stats for media being sent to the remote peer.
      // bytesSent, packetsSent, retransmittedPacketsSent
      break;

    case 'candidate-pair':
      // Stats for an ICE candidate pair. The nominated pair is the active path.
      if (stats.nominated) {
        // currentRoundTripTime: RTT in seconds (multiply by 1000 for ms)
        // availableOutgoingBitrate: estimated available bandwidth
        console.log(`RTT: ${stats.currentRoundTripTime * 1000} ms`);
      }
      break;

    case 'local-candidate':
    case 'remote-candidate':
      // candidateType: 'host', 'srflx', or 'relay'
      // If remote-candidate.candidateType === 'relay', TURN is active.
      console.log(`Candidate type: ${stats.candidateType}`);
      break;
  }
});

Calculating bitrate from cumulative bytes

WebRTC stats report cumulative byte counts, not instantaneous rates. To calculate bitrate, sample the stats at a regular interval and compute the difference:

let previousBytesReceived = 0;
let previousTimestamp     = 0;

setInterval(async () => {
  const report = await peerConnection.getStats();

  report.forEach((stats) => {
    if (stats.type === 'inbound-rtp' && stats.kind === 'video') {
      const bytesDelta = stats.bytesReceived - previousBytesReceived;
      const timeDelta  = (stats.timestamp - previousTimestamp) / 1000; // seconds

      // Convert bytes per second to kilobits per second
      const bitrateKbps = (bytesDelta * 8) / timeDelta / 1000;
      console.log(`Video bitrate: ${bitrateKbps.toFixed(1)} kbps`);

      previousBytesReceived = stats.bytesReceived;
      previousTimestamp     = stats.timestamp;
    }
  });
}, 1000);

Open it in a separate tab while running any of the Codespace demos to see bitrate, packet loss, and ICE state graphed in real time. It is the most powerful WebRTC debugging tool available.

codespace/signaling_server.py

The signaling server is a minimal Python WebSocket server. It maintains a dictionary of rooms, each holding at most two connections. When a message arrives, it is forwarded to the other peer in the same room.

"""Minimal WebSocket signaling server for WebRTC demos.

Course: Multimediaprogrammierung — Chapter 04: WebRTC
Author: Renato Fera P. — TU Ilmenau AMS Group

Run with: python codespace/signaling_server.py
"""

from __future__ import annotations
import asyncio
import json
import logging
import ssl
from pathlib import Path
import websockets
from websockets.asyncio.server import ServerConnection

# ── Logging ─────────────────────────────────────────────────────────────────
logging.basicConfig(
    level=logging.INFO,
    format='%(asctime)s [%(levelname)s] %(message)s',
    datefmt='%H:%M:%S'
)
log = logging.getLogger(__name__)

# ── Room registry ────────────────────────────────────────────────────────────
# rooms maps a room_id (str) to a list of at most 2 WebSocket connections.
# When a peer disconnects, it is removed from its room.
rooms: dict[str, list[ServerConnection]] = {}

# ── Message handler ──────────────────────────────────────────────────────────
async def handler(websocket: ServerConnection) -> None:
    """Handle one WebSocket connection for its lifetime.

    Receives JSON messages from the client, routes them to the other peer
    in the same room, and cleans up when the connection closes.
    """
    room_id: str | None = None

    try:
        async for raw in websocket:
            message = json.loads(raw)
            msg_type = message.get('type')
            room_id  = message.get('room', 'default')

            if msg_type == 'join':
                # Add this peer to the room (create the room if it does not exist).
                if room_id not in rooms:
                    rooms[room_id] = []
                rooms[room_id].append(websocket)
                log.info(f"Peer joined room '{room_id}' ({len(rooms[room_id])}/2 peers)")

                if len(rooms[room_id]) == 2:
                    # Two peers are now in the room — tell the first peer
                    # that a second peer has joined so it can start the offer.
                    first_peer = rooms[room_id][0]
                    await first_peer.send(json.dumps({'type': 'peer-joined'}))

            else:
                # For all other message types (offer, answer, ice),
                # forward the message to the OTHER peer in the room.
                peers = rooms.get(room_id, [])
                for peer in peers:
                    if peer is not websocket:
                        await peer.send(raw)  # forward the raw JSON string unchanged
                        log.info(f"Routed '{msg_type}' in room '{room_id}'")

    except websockets.exceptions.ConnectionClosedOK:
        pass  # Normal disconnect — no error logging needed
    except Exception as e:
        log.error(f"Handler error: {e}")
    finally:
        # Remove this peer from its room on disconnect.
        if room_id and room_id in rooms:
            rooms[room_id] = [p for p in rooms[room_id] if p is not websocket]
            log.info(f"Peer left room '{room_id}' ({len(rooms[room_id])} remaining)")
            if not rooms[room_id]:
                del rooms[room_id]

# ── TLS context ─────────────────────────────────────────────────────────────
def make_ssl_context() -> ssl.SSLContext:
    """Create an SSL context using the self-signed certificate generated by start.sh."""
    ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
    ctx.load_cert_chain(
        certfile='/etc/coturn/turn_server_cert.pem',
        keyfile='/etc/coturn/turn_server_pkey.pem'
    )
    return ctx

# ── Entry point ──────────────────────────────────────────────────────────────
async def main() -> None:
    """Start the WSS signaling server on port 8765."""
    ssl_context = make_ssl_context()
    log.info("Signaling server starting on wss://0.0.0.0:8765")
    async with websockets.serve(handler, '0.0.0.0', 8765, ssl=ssl_context):
        await asyncio.get_running_loop().create_future()  # run forever

if __name__ == '__main__':
    asyncio.run(main())

codespace/start.sh

#!/bin/bash
# start.sh — starts coturn and the signaling server inside the Codespace.
# Runs automatically via devcontainer.json postStartCommand.

set -e  # exit immediately on any error

CERT=/etc/coturn/turn_server_cert.pem
KEY=/etc/coturn/turn_server_pkey.pem

# Generate a self-signed TLS certificate if one does not already exist.
# Both coturn and the signaling server share this certificate.
if [ ! -f "$CERT" ]; then
  echo "Generating self-signed TLS certificate..."
  mkdir -p /etc/coturn
  openssl req -x509 -newkey rsa:2048 -keyout "$KEY" -out "$CERT" \
    -days 365 -nodes -subj "/CN=codespace.local"
  echo "Certificate generated."
fi

# Start coturn in the background.
turnserver -c /workspaces/multimedia_programming_seminars/codespace/coturn.conf &
echo "coturn started (TURNS on port 5349)"

# Start the WebSocket signaling server in the background.
python /workspaces/multimedia_programming_seminars/codespace/signaling_server.py &
echo "Signaling server started (WSS on port 8765)"

echo ""
echo "Both servers are running. Find the public URLs in the Codespace Ports tab."
echo "Replace 'https://' with 'wss://' for the signaling server URL."

# Keep this script alive so the Codespace postStartCommand does not exit.
wait
