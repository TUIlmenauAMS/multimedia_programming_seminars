Demo 4 — ICE & Stats Inspector

04_mm_ice_stats.html · Loopback · Google STUN · Step-by-step ICE gathering, candidate pair selection, annotated getStats()

Both Peer A (offerer) and Peer B (answerer) live in this single page — no camera, no second tab, no copy-pasting. The sole purpose is to watch ICE work in slow motion: candidates gather one by one, the browser selects a winning pair, and getStats() starts reporting live transport metrics. Work through the steps below, reading each explanation before you click.

What's new compared to Demo 3. Demo 3 taught signaling — you moved SDP manually between tabs to feel the friction a signaling server removes. Demo 4 removes that friction entirely so you can focus on the layer below: how ICE actually finds a network path and how you read what the browser reports about it. Demo 5 puts everything together with a real WebSocket signaling server.
STUN is on. The ICE configuration here includes stun:stun.l.google.com:19302. Unlike Demo 1 (which used no STUN and therefore only produced host candidates), this demo also produces a srflx (server-reflexive) candidate — your public IP:port as observed by the STUN server. That srflx candidate is what enables NAT traversal in a real call.

Step-by-Step Demo

Each step runs exactly one part of the handshake. Read the explanation, click the button, then watch the event log and the ICE table update below.

Not started ICE: — Signaling: —
1
Step 1 Create both RTCPeerConnections with Google STUN

Two RTCPeerConnection objects are created — one for each peer — with the same ICE configuration: a single STUN server. This is the only difference from Demo 1, which used an empty iceServers: [] array.

Adding the STUN server causes the browser to send a STUN Binding Request to stun.l.google.com:19302 during ICE gathering. The STUN server replies with your public IP:port (the address your NAT router has assigned to this outbound connection). That reply becomes a server-reflexive (srflx) ICE candidate.

// CONCEPT: RTCConfiguration
The object passed to new RTCPeerConnection(config) controls ICE behaviour for the lifetime of the connection. Key fields:
iceServers — array of {urls} objects. Can mix STUN and TURN.
iceTransportPolicy — "all" (default) tries every candidate type; "relay" forces TURN-only (used in Demo 6 to verify TURN is working).
bundlePolicy — controls whether audio and video share one transport port.
2
Step 2 Peer A creates offer — ICE gathering starts

pcA.addTransceiver('audio', {direction:'recvonly'}) adds a dummy media section to the SDP. Without at least one m= line ICE has no reason to gather candidates. Then createOffer() generates the SDP and setLocalDescription(offer) stores it — this is the call that triggers ICE gathering on Peer A.

Watch the ICE table below fill in as candidates arrive via onicecandidate. Each candidate represents a different network path the browser found. The srflx candidate may take a second longer — it requires the STUN round-trip to complete before it appears.

// CONCEPT: ICE gathering is triggered by setLocalDescription, not createOffer
createOffer() merely generates the SDP text — it does not contact any network. It is setLocalDescription() that locks in the local description and starts the ICE agent. Candidates then fire asynchronously via onicecandidate, one at a time, as the browser discovers them. A null candidate signals end-of-gathering. In Demo 5 (WebSocket signaling) each candidate is forwarded to the remote peer the moment it arrives — this is called trickle ICE (RFC 8838).
3
Step 3 Exchange offer/answer — Peer B's ICE gathering starts

The offer is handed directly to Peer B (simulating the signaling server). Peer B calls setRemoteDescription(offer), then createAnswer(), then setLocalDescription(answer) — which starts Peer B's ICE gathering. Finally the answer goes back to Peer A via setRemoteDescription(answer).

At this point both peers have a complete local and remote description. ICE connectivity checks begin automatically — each peer sends STUN binding requests to every candidate address the other peer has, trying to find a working path.

// CONCEPT: Offer/answer is not symmetric
Only the offerer calls createOffer(); only the answerer calls createAnswer(). The offerer sets its description first (setLocalDescription), then the answerer sets the offer as its remote description before answering. After this step: pcA.localDescription = offer  ·  pcA.remoteDescription = answer
pcB.localDescription = answer  ·  pcB.remoteDescription = offer
4
Step 4 ICE connects — explore the nominated pair and live stats

This step happens automatically — no button needed. ICE runs connectivity checks on every A↔B candidate combination. When a working pair is found and nominated, iceConnectionState becomes connected and the DTLS handshake completes. Watch the status badges above and the event log below.

Once connected, the Nominated Pair and Live Stats sections below populate and update every second.

// CONCEPT: DTLS follows ICE
ICE finds the network path; DTLS secures it. After ICE nominates a candidate pair, a TLS-like handshake runs on that path — the peers exchange certificates and verify the fingerprints they committed to in the SDP (a=fingerprint:). Only after DTLS completes can encrypted media or DataChannel data flow. This is why WebRTC is end-to-end encrypted by design: the fingerprint in the SDP ties the encryption keys to the signaling session.

ICE Candidates — Both Peers

Every candidate gathered by Peer A and Peer B appears here as onicecandidate fires, sorted by priority descending. Higher priority = preferred by ICE. In a real call across the internet you would see host candidates (local LAN addresses) and one or more srflx candidates (public IP:port from the STUN server). A relay candidate requires a TURN server — that is Demo 6.

PeerTypeProtocolAddress : PortPriorityFoundation
Candidates appear after Step 2 and Step 3…
// CONCEPT: Priority formula (RFC 8445 §5.1.2)
Priority = (type_preference × 2²⁴) + (local_preference × 2⁸) + (256 − component).
Type preferences assigned by the browser: host 126  >  prflx 110  >  srflx 100  >  relay 0.
Sorting by priority is therefore equivalent to sorting by candidate type — the table you see above mirrors exactly the order in which ICE tries pairs.

Nominated Candidate Pair

After ICE connectivity checks complete, exactly one candidate pair is nominated — chosen as the winner. All subsequent traffic (DTLS keep-alive, STUN consent checks, and in a real call, RTP media) travels on this path alone. getStats() identifies the nominated pair with nominated: true on a candidate-pair entry.

Not connected yet — the winning pair appears here once ICE completes (Step 4).
