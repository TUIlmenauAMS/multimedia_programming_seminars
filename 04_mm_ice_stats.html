Demo 4 — ICE & Stats Inspector

04_mm_ice_stats.html · No server · Google STUN · Live ICE candidate table & getStats() dashboard

The same manual-signaling P2P video call as Demo 3 — but this time every ICE candidate is also shown in a live, colour-coded table as it arrives, the nominated candidate pair (the actual network path your media is using) is displayed once connected, and a live getStats() dashboard shows real bitrate, packet loss, and round-trip time.

What do host / srflx / relay mean?

Each ICE candidate is one possible network address a peer could be reached at. host is a local network interface address (e.g. your LAN IP) — cheapest, works only on the same network. srflx (server-reflexive) is your public IP:port as seen by the STUN server — works across most home NATs via hole-punching. relay is an address on a TURN server that relays all traffic — used only when no direct path works (not configured in this demo; see Demo 6). The browser tries every candidate pair and picks the best one that actually connects.

→ Full explanation: Chapter §8 ICE  ·  §9 STUN
What is the "selected candidate pair"?

ICE doesn't just gather candidates — it tests every local candidate against every remote candidate (a "candidate pair") with STUN connectivity checks, and whichever pair succeeds with the highest combined priority gets nominated as the active path. All media then flows over that one pair. That's exactly what the "Selected Pair" box below shows once you're connected — the actual addresses your video is traveling between, not just the full candidate list.

→ Full explanation: Chapter §8 ICE
What is getStats() actually reporting?

RTCPeerConnection.getStats() returns a snapshot of the connection's internals — the same data chrome://webrtc-internals graphs. Byte/packet counts are cumulative, not a rate, so bitrate below is calculated by sampling twice, one second apart, and dividing the difference — exactly the pattern in the chapter reference.

// CONCEPT: Each peer has its own view
Tab A's stats dashboard and Tab B's stats dashboard are computed independently — each is reading its own RTCPeerConnection.getStats(). They should broadly agree (Tab A's "outbound" bitrate ≈ Tab B's "inbound" bitrate) but won't be pixel-identical, since each side samples on its own 1-second clock.
// CONCEPT: Priority math
A candidate's priority is roughly (type preference × 2²⁴) + (local preference × 2⁸) + component, with host candidates weighted highest (126), then srflx (100), then relay (0) — so sorting the table by priority is effectively sorting by candidate type. See Chapter §8 for the exact formula.
