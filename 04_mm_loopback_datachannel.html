Demo 1 — RTCPeerConnection Loopback & DataChannel

04_mm_loopback_datachannel.html  ·  No network, no camera, no server required

This demo runs a complete WebRTC handshake entirely inside your browser. Two RTCPeerConnection objects — Peer A and Peer B — exist as JavaScript objects on this page and negotiate directly, with no signaling server, no camera, and no packets leaving your machine. An RTCDataChannel lets them exchange text messages once connected.

The goal is to make every step of the WebRTC handshake visible and legible: the SDP offer, the SDP answer, ICE candidate gathering, and the moment the channel opens. Work through the steps below in order. The Event Log records everything as it happens.

Why loopback? In a real call, Peer A and Peer B would live in different browsers — possibly on different continents. The signaling messages (SDP, ICE candidates) would travel over a WebSocket server. The loopback setup collapses that network into a single page so you can see all the moving parts without network delays or server setup. The WebRTC protocol itself is identical to a real call — only the transport of signaling messages is simulated. Compare this demo with Demo 5, which does the exact same handshake over a real WebSocket signaling server.

How the Handshake Works

Step-by-Step Demo

Work through each step below. Each step runs exactly one part of the WebRTC handshake and explains what just happened in the browser. The full Event Log at the bottom captures everything with timestamps.

1
Step 1 Create RTCPeerConnection objects

Two RTCPeerConnection objects are created — one for each peer — with an empty ICE server list. No STUN server is needed here because both peers are in the same browser; they will find each other using host candidates (local network interface addresses) alone.

Concept: RTCPeerConnection is the central WebRTC object. It manages the entire connection lifecycle: ICE negotiation, DTLS handshake, codec selection, RTP transport, and DataChannel SCTP transport. Think of it as the "audio context" of WebRTC — everything else connects to it.
In Demo 3 and Demo 5, this constructor receives STUN and TURN server URLs so the browser can traverse NAT. Here, we omit them.
2
Step 2 Create DataChannel (Peer A only)

Only Peer A calls createDataChannel(). This must happen before createOffer(), so the channel is declared in the SDP's m=application section. When Peer B later receives the offer and sees m=application, it fires an ondatachannel event — Peer B never calls createDataChannel() itself.

The offerer/answerer asymmetry: In WebRTC, only the offerer creates the DataChannel. The answerer receives it via the ondatachannel event. This asymmetry is fundamental — it reflects which peer initiated the connection. In a real application, whichever peer calls createOffer() first is the offerer.
3
Step 3 Create and exchange SDP offer

pcA.createOffer() asks the browser to generate an SDP description of what Peer A is offering. pcA.setLocalDescription(offer) stores it locally and starts ICE gathering — the browser begins enumerating network interfaces to find candidates. Then the offer is handed directly to Peer B (simulating signaling), which calls setRemoteDescription(offer) to learn what Peer A wants.

ICE gathering starts here. Calling setLocalDescription() is what triggers ICE gathering — not createOffer(). The browser fires onicecandidate events for each candidate it discovers. In Demo 5 these candidates are forwarded over WebSocket; here we call addIceCandidate() directly on the other peer.

Step 4 Create and exchange SDP answer

Peer B now has the offer. It calls createAnswer() to generate its own SDP — confirming the codecs, agreeing on security parameters, and adding its own ICE credentials. pcB.setLocalDescription(answer) stores it and starts Peer B's ICE gathering. Finally, the answer is handed back to Peer A: pcA.setRemoteDescription(answer). Both peers now have complete knowledge of each other — the offer/answer exchange is complete.

After this step: pcA.localDescription = offer  ·  pcA.remoteDescription = answer
pcB.localDescription = answer  ·  pcB.remoteDescription = offer.
ICE connectivity checks are now underway on both sides. Watch the ICE Candidates log below.
5
Step 5 ICE connects — DataChannel opens

ICE connectivity checks run automatically once both peers have a remote description. The browser tests candidate pairs — sending STUN binding requests and checking responses. When a working path is found, the iceConnectionState transitions to connected. The DTLS handshake then completes, establishing encryption. Finally, the SCTP association opens and the RTCDataChannel fires its onopen event.

This step happens automatically — no button needed. Watch the Event Log and the status badges above to see it unfold.

Why no STUN here? Both peers are in the same browser process. Their host candidates — local loopback addresses (127.0.0.1) — are directly reachable without NAT traversal. In Demo 3 and Demo 5, STUN reveals each peer's public IP so they can connect across the internet.

DataChannel — Send Messages Between Peers

Each peer has its own chat panel. Messages sent by Peer A appear as blue on the right in A's view and as received (left) in B's view, and vice versa. This makes the directionality of the data channel explicit — you can see exactly who sent what and who received it.

ICE Candidate Log

As soon as setLocalDescription() is called on each peer, the browser starts ICE gathering: it enumerates local network interfaces and contacts any configured STUN servers. In this loopback demo there are no STUN servers — only host candidates (local IPs) appear. In a real P2P call (Demo 3, Demo 5), you would also see srflx (server-reflexive) candidates, which are the public IPs discovered by a STUN server — necessary for NAT traversal.

SDP Offer — Parsed Breakdown

SDP (Session Description Protocol, RFC 8866) is a plain-text format that describes the session: security fingerprints, ICE credentials, codec parameters, and DataChannel details. It looks cryptic, but every line has a specific meaning. The table below parses the offer SDP line by line, linking each field to its role in the protocol. See Section 6 of the theory page for the full explanation.

SDP is written by the browser, not by you. You never write SDP by hand in a WebRTC application. But reading it is an essential debugging skill — when a call fails, the SDP is almost always where you look first.
