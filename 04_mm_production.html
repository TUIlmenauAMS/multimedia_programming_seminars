Production Pattern — Multi-track · DataChannel · ICE Restart · QoS Stats

This is the reference implementation for a production-quality WebRTC application. It combines everything from Demos 1–6: automatic WSS signaling, STUN + TURN relay, multi-track media (video + audio), a RTCDataChannel chat running alongside the video call, full getStats() QoS monitoring, and robust connection state management including automatic ICE restart on failure.

CONCEPT: Perfect negotiation pattern. When both peers can trigger renegotiation independently (e.g., adding a track, or a network change fires onnegotiationneeded on both sides simultaneously), a naive implementation enters glare: both peers create an offer at the same moment, each tries to set the other's offer as remote description while their own offer is pending, and the signaling state machine breaks. The W3C perfect negotiation pattern resolves this with a simple rule: one peer is designated polite, the other impolite. When there is a collision, the polite peer rolls back its own pending offer and accepts the incoming one. The impolite peer ignores the incoming offer and keeps its own. The result is always a stable, agreed-upon description. In this demo, the second peer to join the room is polite.
CONCEPT: ICE restart. When a connection enters failed state — because a network change broke all previously working candidate pairs — pc.restartIce() generates new ICE credentials (ice-ufrag and ice-pwd) and triggers onnegotiationneeded, which re-runs the full offer/answer exchange with fresh credentials. The existing media session is preserved — tracks are not stopped, no new getUserMedia is needed. This is how production applications recover from WiFi → mobile network switches and VPN connect/disconnect events. restartIce() is the modern API (Chrome 77+, Firefox 70+); the older createOffer({ iceRestart: true }) is equivalent but requires manual signaling.
