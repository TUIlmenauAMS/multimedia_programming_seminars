TURN Relay Verification

This demo adds a TURN relay server (coturn) to the ICE configuration from Demo 5. The central question is: is traffic going direct (srflx) or through the TURN relay? The candidate type badge below answers that live, updated every second from getStats().

Teaching focus: TURNS URL format · iceTransportPolicy: "relay" · verifying relay via getStats() · long-term vs time-limited credentials · bandwidth cost of TURN.

See Sections 12–13 of the theory HTML for the full TURN and coturn explanation.

CONCEPT: TURN bandwidth cost. When the selected candidate type is relay, every byte of media passes through the coturn server: Peer A → coturn → Peer B, and back. This doubles the bandwidth consumed on the TURN server and adds at least one extra network hop of latency. The stats dashboard above shows bytes sent/received so you can see the cost directly. This is why relay candidates have the lowest ICE priority — they are the last resort, used only when no direct path is available.
CONCEPT: Credential security — long-term vs time-limited. The credentials in this demo (webrtc / seminar04) are long-term credentials: a static username and password in coturn.conf. Simple, but they cannot be revoked per-session and are valid indefinitely. In production, backends generate time-limited credentials: the username encodes a Unix timestamp (the expiry), and the password is HMAC-SHA1(shared_secret, username). Once the timestamp passes, the credential is invalid. coturn verifies the HMAC against the shared secret, so a leaked credential becomes useless after it expires. This is the production standard (RFC 8656 §9.2).
