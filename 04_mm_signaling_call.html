Demo 5: Automatic Signaling Call

A real two-tab video call using a WebSocket signaling server running in a GitHub Codespace. No copy-paste — offers, answers, and ICE candidates are exchanged automatically over WSS. Open this page in two browser tabs, paste the same Codespace URL, join the same room, and the call connects by itself.

Compare the event log below with Demo 3 (manual SDP copy-paste): every message you copied by hand there is sent automatically here. The signaling server is a dumb router — it has no knowledge of SDP or WebRTC. It simply forwards JSON between two peers in a room.

Step 1 — Connect to Codespace Signaling Server
Before you start: Launch the Codespace from the repository (Code → Codespaces → Create codespace on main), wait for start.sh to run, then open the Ports tab and copy the forwarded URL for port 8765. Replace https:// with wss:// before pasting it below.

Event Log — Signaling Messages & WebRTC State Changes
CONCEPT: Signaling server as a dumb router. The server has no knowledge of SDP, ICE, or WebRTC. It receives a JSON message from one peer and forwards it to the other peer in the same room — that is all it does. Open codespace/signaling_server.py and count the lines: the core routing logic fits in under 20 lines of Python. The intelligence is entirely in the browser.
CONCEPT: Caller vs callee asymmetry. One peer must create the offer. In this demo, the first peer to join the room becomes the caller — the server sends it a peer-joined message when the second peer arrives, which triggers createOffer(). The second peer (callee) waits for the offer, then answers. This asymmetry is fundamental to WebRTC's offer/answer model.
CONCEPT: Trickle ICE over WebSocket. ICE candidates are sent to the remote peer as they are discovered — not bundled into the SDP. Watch the event log: you will see ice → entries arriving after the offer/answer exchange. Trickle ICE reduces call setup time because connectivity checks begin before the slowest candidate (TURN allocation) has even arrived.
CONCEPT: ICE candidate queueing. ICE candidates from the remote peer may arrive via the signaling channel before setRemoteDescription() has been called. Calling addIceCandidate() before setRemoteDescription() throws an error. The solution is to queue incoming candidates and add them after setRemoteDescription() completes. See pendingCandidates in the JavaScript below.
